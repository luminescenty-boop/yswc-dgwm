# 《亚瑟王朝之帝国崛起》阶段二、三分析报告

## 结论

原始 JAR 有效，核心玩法是离线运行的 2D 战略/战棋游戏。代码和资源都可以被完整盘点，已经在 FreeJ2ME 中实际启动并走通了开场、声音选项、主菜单、新的征程和首关开场对话。移植到现代 iPhone 横屏触摸版本是可行的，推荐重新实现现代客户端，而不是把 J2ME 画布直接放进外壳。

## 安装包信息

- 文件：`java游戏亚瑟王朝之帝国崛起_大屏通用版(240x320).jar`
- JAR 大小：1,133,664 bytes
- SHA-256：`b4e8682358e6a4d08e65f94d696567673190cb54c4e31627c7e2552ee87ceb0e`
- MIDlet：`GameMidlet`
- 名称：亚瑟王朝之帝国崛起
- 厂商字段：万联国通
- 版本：1.0
- 目标平台：CLDC 1.0 / MIDP 2.0
- 原始画布：240×320，竖屏
- 资源时间戳：2011-01-15

## 代码结构

JAR 内有 17 个类，类名被压缩为单字母，但职责可以通过调用关系和资源访问还原：

| 类 | 还原出的职责 |
| --- | --- |
| `GameMidlet` | MIDlet 生命周期 |
| `p` | 主 Canvas、输入映射、游戏线程、RMS 存档、声音控制 |
| `e` | 主游戏场景、地图、任务、单位和战役状态 |
| `a` | 战斗场景与战斗动画 |
| `d` | 启动画面、厂商 Logo、声音询问和过场 |
| `f` | 菜单、对话框、文字和 UI 容器 |
| `m` | 地图单位、移动和动作实体 |
| `i/j/l` | 精灵表、图块、裁剪区域和图片缓存 |
| `k/c` | 字体、语言字符串和文字排版 |
| `h` | MIDI 播放器封装 |
| `g` | 旧的外部网页跳转 |
| `b/n/o` | 资源读取、随机/辅助逻辑和定时任务 |

CFR 反编译后，最大核心类 `e` 约 6,100 行、约 105 个方法；它同时包含地图、任务、单位、剧情和战役状态，因此后续应按系统拆分，不能直接把这个类机械翻译成 Swift 或 GDScript。

## 资源盘点

- 254 张 PNG。
- 73 个 `.sprite` 精灵定义文件。
- 16 个 MIDI 文件，包括标题、场景、战斗、胜利和失败音乐。
- 12 个 `pic/s0` 到 `pic/s11` 二进制关卡/剧情数据文件。
- `pic/tiles0.prop`、`pic/tiles0.sprite` 和 37 个地图图块。
- `pic/units.bin`，约 209 bytes，包含单位相关数据。
- `c.java` 中有 289 条语言/剧情字符串。
- 最大资源包括 `pic/menumain.png`（428×350）、`cg/cg.png`（523×394）和大量 240 像素宽的战斗/过场图。

许多 PNG 不是完整图片，而是精灵表或单帧图块；`.sprite` 文件保存裁剪坐标、帧序列和对齐方式。因此单独打开时会看到很多相似的小图，这是原版的正常资源组织方式，不是素材丢失。高清化时必须先按 `.sprite` 定义重组动画和角色，再处理成现代资源。

## 已确认的玩法内容

语言字符串和资源表确认包含：

- 新的征程、选择关卡、保存/载入、设置和帮助。
- 地图移动、进攻、购买、占领、修补、召唤、结束回合。
- 建筑、城市、金币、治疗和部队生产。
- 士兵、武士、斗士、射手、法师、水占师、传令兵、骑兵、龙骑士、将军等单位体系。
- 多个战役关卡，包含营救亲王、保护城市、消灭援军、占领城堡和最终决战等目标。
- 三个 RMS 存档槽，名称为 `save0`、`save1`、`save2`；另有 `download` 数据槽。

代码主循环以约 65ms 为目标间隔，约 15 FPS；iPhone 版可以采用独立逻辑时钟并以 60 FPS 绘制，保持原版回合和动画节奏。

## 实际运行验证

使用 FreeJ2ME 在 240×320 原始尺寸下运行，已得到以下结果：

1. JAR 能正常加载并创建 MIDlet。
2. 标题 Logo 和“是否开启音效”画面正常显示。
3. 自动进入开场过场，能够跳过开场动画。
4. “新的征程”等主菜单正常绘制。
5. 进入新的征程后，首关地图和开场对话正常显示。
6. 地图画面包含草地、道路、树木、岩石、建筑、骑士和 HUD 图层。

本次云端实机模拟已验证到首关开场对话；战斗操作和保存/读取的具体按键路径尚未在模拟器中完整跑完。它们的实现入口、战斗资源和三槽 RMS 读写代码已经确认，后续做现代工程时仍应补一次逐项回归。

云环境没有可用的 MIDI 音频线路，FreeJ2ME 报告 `Couldn't load MIDI file: Can not open line`。这是测试主机音频输出限制，资源和 MIDI 文件本身能够被读取，不是游戏逻辑失败。

## 网络和外部依赖

核心玩法不依赖网络。代码中发现一个旧的 `platformRequest` 地址：

`http://gamepie.g188.net/gamecms/go/jpgd`

它属于外部网页跳转或下载入口，现代复刻版可以移除，避免 iOS 安全策略和失效网页影响主流程。

## 后续可行性评估

### 可行部分

- 2D 地图和战斗资源完整，适合重建为 Godot 4 或 SpriteKit 场景。
- 关卡数据、单位数据和剧情字符串仍在包内。
- 没有必须恢复的联网服务。
- iPhone 12 及后续机型的性能远高于原始目标设备。
- 横屏版可以保留 240×320 的逻辑坐标，再改用安全区域和自适应 UI。

### 主要工作量

- 将 `e` 拆成地图、战役、任务、单位和剧情模块。
- 解析并重建 `.sprite` 精灵定义。
- 把键盘事件改成点按、拖动、长按和可选虚拟方向键。
- 将位图文字改成高清字体，不能简单放大原始中文位图。
- 逐帧处理人物和战斗动画，修复透明边缘和低分辨率锯齿。
- 用现代本地存档替代 RMS，并决定是否兼容旧存档。
- 在 macOS/Xcode 上进行最终 iOS 真机签名和测试。

### 预计规模

在不改变玩法、素材风格保持接近原版的前提下，第一阶段可行目标是：先完成一个能横屏触摸运行的首关测试版，再逐关补齐内容。代码移植本身属于中等规模；高清素材和逐帧动画修整是最大的不确定项。当前证据支持继续进入工程骨架和输入方案阶段，不需要先解决联网或服务器问题。

## 当前限制

- 还没有生成现代 iOS 工程。
- 还没有在真实 iPhone 12 上签名安装。
- 云环境中 MIDI 播放无法验证。
- 原始类名被混淆，部分逻辑需要通过运行和数据交叉确认。
- 战斗和存档需要在下一阶段的现代工程中补充自动化回归测试。
- 本报告只记录技术分析；如果要公开发布或商业化，仍需单独完成版权和发行权确认。
